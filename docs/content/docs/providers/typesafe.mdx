The TypeSafe provider lets TypeSafe's Jev model choose and run a Composio tool from a plain-language request, and hands you a confidence score with every decision.

Jev is not an LLM and has no tool calling. It takes a state plus typed questions and returns calibrated probabilities in about 100 ms. The provider compiles your Composio tools into those questions, asks Jev, and gives you back one of three things:

- A `call`: a tool and every required argument.
- A `partial` call: a tool, the arguments Jev bound, and the required arguments still missing.
- An `abstain`: no tool call, with a reason and the ranked candidates.

Unlike the other providers, this one never hands tools to a model that writes text. You call `decide`, inspect what came back, and then call `execute`.

<Callout type="info">
`@typesafe-ai/sdk` and `typesafe-sdk` are young 0.x packages, and 0.6.0 was a breaking release, so the provider accepts `>=0.6.0 <0.7.0` only. Pin an exact version. The TypeScript package needs Node.js 24.17 or newer, because `@typesafe-ai/sdk` 0.6.0 terminates the process after a cancelled request on older releases, even when you catch the error.
</Callout>

from composio import Composio

## Most decisions are partial calls, and that is the point

Jev answers closed questions. It never writes text. So the provider sorts every tool argument into one of two groups:

- **Closed-set arguments** are enums, booleans, and arrays of enum values. Each one becomes a question, and Jev binds the value.
- **Open-ended arguments** are everything else: free text, numbers, dates, IDs, and objects. They get no question. You supply them.

A `partial` decision names the tool, the arguments Jev bound, and the required arguments still missing. Complete it with caller arguments in `execute`:

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
if decision["kind"] == "partial":
    print(decision["missing"])  # [["owner"], ["repo"]]
    provider.execute(
        "user_123",
        decision,
        arguments={"owner": "ComposioHQ", "repo": "composio"},
    )
```

Caller arguments win over Jev-bound values. Only an absent key counts as missing, so `None` is a value.
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
if (decision.kind === 'partial') {
  console.log(decision.missing); // [['owner'], ['repo']]
  await provider.execute('user_123', decision, {
    arguments: { owner: 'ComposioHQ', repo: 'composio' },
  });
}
```

Caller arguments win over Jev-bound values. Only `undefined` counts as missing, so `null` is a value.
</Tab>
</Tabs>

If you already know some arguments before deciding, pass them to `decide` as `arguments`. They get no question and do not affect the confidence.

Every closed-set question has a "not stated" outcome. When the request does not mention a required argument, it lands in `missing` instead of being bound to the nearest option. When it does not mention an optional argument, the argument is left out. The provider never injects a schema default, so server-side defaults stay in charge.

To let Jev bind an argument that is free text in the schema, turn it into an enum with a [schema modifier](/docs/tools-direct/modify-tool-behavior/schema-modifiers):

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
from composio import schema_modifier


@schema_modifier(tools=["GITHUB_LIST_REPOSITORY_ISSUES"])
def repo_as_enum(tool, toolkit, schema):
    schema.input_parameters["properties"]["repo"]["enum"] = [
        "composio",
        "docs",
        "examples",
    ]
    return schema


tool_set = composio.tools.get(
    user_id="user_123",
    tools=["GITHUB_LIST_REPOSITORY_ISSUES"],
    modifiers=[repo_as_enum],
)
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
const toolSet = await composio.tools.get(
  'user_123',
  { tools: ['GITHUB_LIST_REPOSITORY_ISSUES'] },
  {
    modifySchema: ({ schema }) => {
      const repo = schema.inputParameters?.properties?.repo;
      if (repo) repo.enum = ['composio', 'docs', 'examples'];
      return schema;
    },
  }
);
```
</Tab>

Session meta tools from `session.tools()` work, but their arguments are open-ended, so they yield near-empty partial calls. Prefer `composio.tools.get()`.

## What the confidence means

`confidence` is the score of the least certain judgement the call depends on: the routing answer, the action gate, and every required argument Jev bound. It is _not_ a calibrated probability that the whole call is correct. Use it to rank and to gate, and read `judgements` when you need the parts.

An optional argument with a weak answer is dropped, listed in `dropped`, and does not lower the confidence. A required argument with a weak answer moves to `missing`, and its guess is kept in `suggestions`.

## When the provider abstains

An `abstain` carries a `reason` and the ranked `candidates`:

| Reason | Meaning |
| --- | --- |
| `no_tools` | The tool set is empty. No request is sent. |
| `empty_state` | The request is empty. No request is sent. |
| `no_action_requested` | The request asks for an explanation, or says not to do something. |
| `none_fit` | No tool carries out the request. |
| `low_confidence` | The best tool is below the routing threshold. |

An abstention means only that the model judged so. API failures, timeouts, rate limits, and malformed responses raise typed errors instead: `TypesafeApiError`, whose `reason` is one of `rate_limit`, `timeout`, `connection`, `authentication`, `server_error`, `request_rejected`, or `unknown` (TypeScript adds `aborted`), and `TypesafeMalformedResponseError`. They never come back as an abstention. Error messages hold a status code and a request ID, and never your state, argument values, or response content.

## Thresholds

| Threshold | Default | Applies to |
| --- | --- | --- |
| `routing` | 0.6 | The routing answer. 0.9 for a destructive tool. |
| `gate` | 0.3 | The mean of three "is the user asking for an action now" answers. |
| `argument` | 0.6 | Each argument Jev binds. |

These follow TypeSafe's guidance, which calls them examples to tune. Set them per provider or per `decide` call:

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
provider = TypesafeProvider(thresholds={"routing": 0.7, "argument": 0.8})

provider.decide(tool_set, request, thresholds={"gate": 0.5})
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
const provider = new TypesafeProvider({
  thresholds: { routing: 0.7, argument: 0.8 },
});

await provider.decide(toolSet, request, { thresholds: { gate: 0.5 } });
```
</Tab>
</Tabs>

`jev-latest` is the default model, and it moves. A new model can shift what a threshold means, so pin a model in production with the `model` option. Use the full version: the API rejects a short ID such as `jev-1.13`. Every decision echoes the version it resolved to in `meta.model` (`meta["model"]` in Python), which is the value to pin.

## Destructive tools need confirmation

A tool tagged `destructiveHint` routes at a threshold of 0.9, and its decision asks for confirmation. `execute` refuses it until you confirm explicitly:

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
provider.execute("user_123", decision, confirm=True)
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
await provider.execute('user_123', decision, { confirm: true });
```
</Tab>
</Tabs>

`execute` decides from the decision's stored `risk` class, not from the confirmation flag alone, so clearing that flag does not skip the prompt. No threshold lowers the 0.9 floor. When the state comes from an untrusted source, leave destructive tools out of the tool set.

## Request and context

State is a string, or an object with `request` and `context`. Put what the user asked for in `request`, and supporting material such as an email thread or a record in `context`.

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
provider.decide(
    tool_set,
    {
        "request": "Label this issue as a bug",
        "context": {"issue": {"title": "Login fails", "body": "..."}},
    },
)
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
await provider.decide(toolSet, {
  request: 'Label this issue as a bug',
  context: { issue: { title: 'Login fails', body: '...' } },
});
```
</Tab>
</Tabs>

By default the split is structural. Routing and the action gate see `request` only, so text inside `context` cannot change which tool is picked or whether any action is taken. Only argument questions see `context`. This costs a second request.

What this does not cover: `context` can still move closed-set argument values, a string state has no split, and `request` is trusted input. Set the context scope to `all` when you need `context` to take part in routing. That opts out of the separation.

A state object takes `request` and `context` only. Any other top-level key is never sent, so it raises `TypesafeInvalidOptionsError` instead of being dropped silently. So does a value that is not JSON, such as a date, a big integer, a set, `NaN`, or a class instance. Serialize those before you pass them.

## Decisions are plain JSON

A decision survives `JSON.stringify` and `json.dumps`, so you can queue it for approval and run it later. `execute` needs no tool set and makes no request to TypeSafe. Validate a stored decision yourself with the exported `TypesafeDecisionSchema` (TypeScript) or `parse_decision` (Python).

A stored decision is only as trustworthy as its storage: whoever can edit it can edit `risk` too. Sign a decision, or derive it again with `decide`, when it crosses a trust boundary such as an approval UI or a shared queue. It runs against the toolkit version that resolves at execution time, which can differ from the version recorded in `meta`. A decision made by one SDK is not portable to the other.

`execute` also accepts the [session](/docs/how-composio-works) that produced the tools instead of a user ID. A session takes no execution options and no modifiers.

## Companion helpers

Both helpers work with any other Composio provider, so you can keep your existing agent and add Jev alongside it.

### Shortlist tools before an LLM sees them

Rank raw tools against a request, keep the top `k`, and hand those to an LLM provider. It accepts up to 254 tools.

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
raw = composio.tools.get_raw_composio_tools(toolkits=["github"], limit=100)
shortlist = provider.shortlist_tools(raw, "open an issue", k=5)
openai_tools = openai_composio.tools.get(
    user_id="user_123",
    tools=[tool.slug for tool in shortlist["tools"]],
)
```

`ashortlist_tools` is the async form.
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
const raw = await composio.tools.getRawComposioTools({ toolkits: ['github'], limit: 100 });
const { tools, scores } = await provider.shortlistTools(raw, 'open an issue', { k: 5 });
const openaiTools = await openaiComposio.tools.get('user_123', {
  tools: tools.map(tool => tool.slug),
});
```
</Tab>
</Tabs>

### Veto tool calls that do not match the request

The confidence gate is a [before-execution modifier](/docs/tools-direct/modify-tool-behavior/before-execution-modifiers) that asks Jev whether a tool call an LLM proposed matches what the user asked for, and vetoes it when it does not.

<Tabs groupId="language" items={["Python", "TypeScript"]} persist>
<Tab value="Python">
```python
# One gate per agent run. Reuse it for every retry inside that run.
gate = provider.confidence_gate(
    tools=raw,
    # user-authored text only, never LLM output
    get_request=lambda context: user_message,
    redact_arguments=lambda slug, arguments: {**arguments, "password": "[redacted]"},
)

composio.tools.execute(
    "GITHUB_CREATE_AN_ISSUE",
    arguments,
    user_id="user_123",
    modifiers=[gate],
)
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
// One gate per agent run. Reuse it for every retry inside that run.
const gate = provider.confidenceGate({
  tools: raw,
  getRequest: () => userMessage, // user-authored text only, never LLM output
  redactArguments: (slug, args) => ({ ...args, password: '[redacted]' }),
});

await composio.tools.execute('GITHUB_CREATE_AN_ISSUE', params, { beforeExecute: gate });
```
</Tab>
</Tabs>

Things worth knowing about the gate:

- A veto raises `TypesafeGateVetoError`. After three vetoes (tunable) the gate blocks every later call in the run, so a hijacked LLM cannot vary arguments until one passes. Create a fresh gate for each new run, never share one across users or runs, and never recreate it for each retry.
- One gate checks one call at a time, so concurrent calls cannot slip past the veto limit. Separate gates run in parallel.
- When TypeSafe cannot be reached the gate blocks with `TypesafeGateUnavailableError`. Switching the unavailable mode to `allow` lets those calls through and reports each one to the bypass callback. A tool the gate was not given, an oversized call, arguments or context that are not JSON, and a malformed response always block.
- The redactor gets a copy of the arguments, so the call that runs never changes. It must _mask_ what it got: the same JSON structure (same keys, same array lengths) with every leaf replaced by a value of the same JSON type. A redactor that deletes or adds a key, changes an array's length, or retypes a value blocks the call, because Jev must approve exactly the call that runs.
- The gate checks that a call is consistent with the request. It is not an authorization check. File uploads run before the modifier, so a veto happens after the upload.
- The gate covers direct execution only. A session applies no modifiers on `session.execute`.

## What leaves for TypeSafe

Sent to `api.typesafe.ai`: the state, tool names and descriptions (custom tools included), enum values, and the arguments of calls you gate.

Never sent: your Composio API key, user IDs, connected account IDs, and custom auth parameters.

Check how [TypeSafe](https://docs.typesafe.ai) retains request data before you send personal data. A client the provider builds logs at level `warn` even when `TYPESAFE_LOG_LEVEL=debug` is set, because `debug` prints request bodies, state included. A client you inject logs however you configured it. The TypeSafe SDK honors `TYPESAFE_BASE_URL`, so your API key and your state go to whatever host that variable names.

## Limits

- One decision per `decide` call. A multi-intent request such as "create an issue and notify Slack" is not split.
- A tool set holds at most 254 tools. More raises `TypesafeLimitError`.
- A state that exceeds the request budget raises `TypesafeLimitError`. The provider never truncates state.
- Closed-set properties nested inside object arguments are open-ended.
- Root-level `allOf`, `anyOf`, and `oneOf` raise `TypesafeInvalidOptionsError` when wrapping a tool. Use a flat object schema with top-level `properties` and `required`.
